# Research: Wrapper Vault Factory (Phase 0)

Decisions and rationale grounding [plan.md](./plan.md) and [spec.md](./spec.md). Sources: direct read of `contracts/src/vault/SparkPointVault.sol`, `contracts/src/interfaces/ISparkPointVault.sol`, the existing Foundry suites (`contracts/test/{fuzz,fork,invariant,refute}`), `services/agent/src/sparkpoint_agent/chain/vault_reader.py`, `apps/web/src/lib/chain/*`, the `010-universal-vaults` companion artifacts, the SparkPoint Constitution v1.3.0 (`.specify/memory/constitution.md`), the Morpho ERC-4626 / Vaults V1.1 + V2 docs, and an adversarial review of the first draft.

> **Framing:** every decision below is **contingent on the Phase 0 governance gate** ([plan.md](./plan.md) Constitution Check → **GATE BLOCKED**). None of it is implemented until the operator ratifies the super-majority amendment (US1 / FR-001). Research is allowed pre-ratification; code is not.

## D0 — The governance gate is real; a scope note is NOT available here (contrast 007)

**Decision**: Treat this feature as **BLOCKED pending a super-majority constitution amendment**, and author the amendment as an operator decision rather than self-clearing the gate with a recorded scope note.

**Rationale**: 007 (Universal Swap) cleared IV.5 with a **recorded scope note** because its surface — a user-signed EOA swap on Uniswap/Synthra — was **already outside** the deterministic-policy / vault boundary that IV.5 governs; broadening its token set didn't widen what the policy engine or a vault could reach. Here the situation is categorically different: a `SparkPointMorphoVault` is a **SparkPoint vault that custodies pooled user funds and directs them into Morpho** — precisely the custodied-funds execution path IV.5 binds ("interaction with any other protocol MUST be impossible by construction"). It also adds vaults beyond V's "SINGLE conservative Aave Yield Vault" and re-opens VII's explicitly deferred multi-vault/additional-protocol scope. Governance is explicit that custody-touching changes "require SUPER-MAJORITY approval + explicit re-ratification" and "MUST NOT be made implicitly through implementation. An agent may NOT self-authorize this (ObraHaus playbook 2.6)." A scope note would be exactly that forbidden implicit self-authorization. **Rejected**: reusing the 007 scope-note pattern — it is the wrong instrument for a custody-surface change.

## D1 — Wrapper vault route, not "curator-only" or "point users at raw Morpho"

**Decision**: Ship a **branded ERC-4626 wrapper** (`SparkPointMorphoVault`) that holds a single Morpho vault's shares on behalf of pooled depositors, rather than (a) only becoming a Morpho **curator** and pointing users at the raw Morpho vault, or (b) building a bespoke strategy vault.

**Rationale**: The brief asks for **branded** vaults that charge **SparkPoint's own** performance fee and that appear in the SparkPoint app + admin. A wrapper gives SparkPoint its own share token (branding), its own ≤20% profit-only HWM fee spine (identical to `SparkPointVault.sol`, so the fee code, tests, and admin surfaces are reused), and a single fixed target per instance (single-purpose, N5). The **curator-only** route (setFee on a MetaMorpho V1.1 / Vaults V2 the operator curates) is **complementary, not a substitute** — it routes a *second* curator-style cut to the SparkPoint treasury and is the source of the **double fee** we must disclose (D6); it does not give a branded SparkPoint share or app-native deposit surface. A bespoke strategy vault is exactly the deferred multi-strategy scope VII forbids. **Rejected**: curator-only (no branding/app surface) and bespoke strategy (forbidden scope). The wrapper reads/acts on Morpho purely through the standard `IERC4626` interface, so it is agnostic to MetaMorpho V1.1 vs Vaults V2 underlyings (subject to D3).

## D2 — CREATE2 **full-bytecode** deploys, NOT EIP-1167 minimal-proxy clones (N5)

**Decision**: `SparkPointVaultFactory` deploys the **complete** `SparkPointMorphoVault` runtime bytecode for each instance via **CREATE2** (deterministic address from `keccak256(bytecode ++ constructor args, salt)`), and does **not** use OZ `Clones` / EIP-1167 minimal proxies.

**Rationale**: A minimal-proxy clone is a ~45-byte contract that `delegatecall`s **all** logic into a shared implementation address. That means (1) every clone's behaviour is defined by code at another address, and (2) if that implementation is itself a proxy or is selfdestructable/replaceable, every clone changes behaviour — a delegatecall-to-implementation upgrade surface. N5 requires a **non-upgradeable, single-purpose** vault and the architecture explicitly forbids "delegatecall-to-impl." Full-bytecode deploys make each instance genuinely immutable and self-contained: `RefuteN5Morpho.t.sol` asserts the deployed runtime **code hash equals the full `SparkPointMorphoVault` hash**, not a 45-byte proxy, and that there is no `delegatecall`, `upgradeTo`, or implementation-slot. CREATE2 (over plain CREATE) is chosen so the admin/manage UI can show a **deterministic, pre-computable** address and so redeploy-to-occupied-salt can be refused (FR-018). **Rejected**: `Clones.clone`/`cloneDeterministic` — cheaper gas but reintroduces exactly the upgrade/behaviour-swap surface N5 outlaws. The higher per-deploy gas is an accepted cost (deploys are rare, admin-initiated).

## D3 — Non-rebasing accounting: `totalAssets` via `convertToAssets`, `maxWithdraw` clamp, and the Vaults V2 `max*==0` trap

**Decision**:
- `totalAssets()` = `morphoVault.convertToAssets(morphoVault.balanceOf(address(this)))` — never a raw token `balanceOf`.
- `maxWithdraw(owner)` / `maxRedeem(owner)` are **clamped** to the underlying's currently withdrawable liquidity: `min(userShareValue, morphoVault.maxWithdraw(address(this)))`.
- For **Morpho Vaults V2** underlyings, whose `maxDeposit`/`maxWithdraw`/`maxRedeem` **return 0 by design**, derive availability from the underlying **market/liquidity state** rather than reading `max*==0` as "nothing available."

**Rationale**:
- The Aave `SparkPointVault` set `totalAssets() = aUSDC.balanceOf(this)` because aTokens **rebase** (balance grows with yield). Morpho vault **shares do not rebase**; the share *count* is fixed while the *price* (`convertToAssets`) rises. Reading a raw balance would freeze share value and mis-price everything, corrupting the HWM fee. `convertToAssets` is the honest, standard read.
- ERC-4626 requires that `maxWithdraw` reflect what is **actually withdrawable now**, and that a `withdraw(maxWithdraw)` not revert. Morpho vaults can have only **partial** liquidity (assets deployed into markets/allocations). Without the clamp, a user's `maxWithdraw` would report their full share value, and a full-ask withdraw would revert when Morpho can't source it — breaking the N2 partial-exit guarantee. Clamping to `morphoVault.maxWithdraw(this)` makes partial exits succeed up to available liquidity and the fork test (`VaultMorphoFork.t.sol`) proves 100% of users can withdraw their available pro-rata share even at drained liquidity, offline + paused.
- **The V2 trap**: Morpho **Vaults V2** intentionally return `0` from the ERC-4626 `max*` view functions (liquidity is async / allocation-dependent). A naïve `min(x, 0)` clamp would make **every** withdraw report 0 and lock funds — a catastrophic N2 violation. So for a V2 underlying the wrapper derives withdrawable liquidity from the vault's market/allocation state (idle + instantly-redeemable), and treats `max*==0` as "unknown, derive," never as "zero." This branch is unit + fork tested against a seeded V2 test vault.

**Rounding**: `convertToAssets` rounds **down**; the HWM fee math must use the rounded-down `totalAssets` and mint fee-shares only on realized profit above HWM, so rounding can never push the fee into principal (invariant `PerformanceFeeMorpho.t.sol`). **Rejected**: trusting `max*` uniformly (breaks V2), and raw-balance `totalAssets` (breaks non-rebasing pricing).

## D4 — Fee spine identical to the Aave vault: profit-only HWM, minted as shares, ≤20%

**Decision**: Reuse the exact `SparkPointVault.sol` fee mechanism — profit-only, high-water-mark-gated performance fee **minted as fee-shares** to `feeRecipient`, default **1000 bps**, hard cap **2000 bps** — in `SparkPointMorphoVault`.

**Rationale**: It is already audited, invariant-tested (`contracts/test/invariant/PerformanceFee.t.sol`, `fuzz/PerformanceFee.t.sol`), and constitution-compliant (V: 0 mgmt fee, 0 fee on principal, ≤20% profit-only HWM). Reusing it keeps the two vault types economically consistent and lets the admin fee surfaces + confirm gate stay uniform. The only adaptation is that "profit" is measured against `convertToAssets`-based `totalAssets` (D3) rather than the rebasing aToken balance; the HWM is stored in the same share-price terms. **Rejected**: a management fee or a different fee model — needless divergence + a new audit surface.

## D5 — Guardian = OZ `TimelockController`, pause-deposits-only; manage actions queued through it

**Decision**: Each wrapper's guardian is an OZ `TimelockController` (the same pattern as the Aave vault's `0x0A21…d720`). The wrapper's guardian power is **pause-DEPOSITS-only**. All manage actions from `/admin/vaults` — `pause`/unpause, `setFee`, `setFeeRecipient`, cap adjustments — are **queued on the timelock** (queue → wait delay → execute), never instant admin writes. `useVaultManage.ts` builds and submits these operations; `killswitch/page.tsx` reflects `paused()`/`guardian()`.

**Rationale**: N2 + Guardrail IV.3 require the killswitch to be **pause-only** (never block withdrawals), and Governance treats custody-adjacent economic changes (fees) as sensitive. A timelock bounds blast radius: a compromised admin session cannot instantly change fees or recipients — the queued op is visible on-chain and only executes after the delay, giving users time to exit (N2 withdraw-always is never gated). The wrapper's constructor **rejects a non-timelock guardian** (fail-closed, FR-012) so an instance can't be deployed with an instant-control guardian. The admin manage UI shows pending timelock ops alongside the 010 live-state read (010 US3 ↔ 011 US4). **Rejected**: a plain `Ownable` admin with instant `setFee`/pause — too much blast radius for a custody-adjacent control; contradicts the existing pause-only, timelock-governed model.

## D6 — Double fee: disclose honestly, never hide (Principle III)

**Decision**: When a wrapper's underlying is a Morpho vault that already charges a native curator/performance fee (MetaMorpho V1.1 `setFee` ≤50%, or Vaults V2 curator perf ≤50% + mgmt ≤5%/yr), the wrapper's **own** ≤20% HWM fee **stacks on top**. Every surface that shows the wrapper's fee or APY MUST disclose (a) the stacked structure and (b) that the yield source is the Morpho vault, **not** Aave. The confirm gate (`useVaultConfirm.tsx`), `/admin/vaults`, `/fees`, and any chat/portfolio card carry this disclosure. Net APY shown is **net of both** fees.

**Rationale**: Principle III requires yield "reported net of everything" and figures that are "current + verifiable," and forbids implying an Aave source when there isn't one. The wrapper reads the underlying's net APY (via the Morpho GraphQL API on mainnet — the 010 data feed — or on-chain-derived on testnet) which is already net of the curator fee, then subtracts its own HWM fee for the displayed net. Hiding the stack would be a direct III violation and a trust liability. The revenue model explicitly anticipates this: "the same performance-fee spine extends to higher-alpha vaults / curator-style cut" — so a SparkPoint-curated underlying can route a curator fee to the treasury **in addition to** the wrapper fee; that is legitimate **only if disclosed**. **Rejected**: showing a single blended fee or an Aave-flavored APY — misrepresents source + magnitude.

## D7 — Curated, on-chain-gated allowlist preserves "impossible by construction"

**Decision**: The factory holds an **on-chain curated allowlist** of vetted Morpho vault addresses (per chain), mutable only by the admin, and **refuses by construction** to deploy a wrapper whose target is not on it. Deployed wrappers are immutable and hold a single target, so de-listing a target after deployment does not affect existing wrappers' withdrawals (allowlist membership never gates N2).

**Rationale**: The amendment widens IV.5's whitelist to "curated Morpho vaults," but IV.5's teeth are "interaction with any other protocol MUST be **impossible by construction**." The allowlist gate is that construction: even a compromised admin session cannot wrap a malicious/un-vetted ERC-4626 (it's not on the list), bounding blast radius. Making it **on-chain** (not just a UI filter) means the guarantee holds regardless of the frontend. Withdrawals deliberately **do not** consult the allowlist — a de-listed underlying must still let existing users exit (N2). **Rejected**: an off-chain/UI-only allowlist (bypassable), or wrapping arbitrary admin-supplied addresses (defeats the amendment's safety premise).

## D8 — Reuse the 010 registry/reader; no per-vault frontend hardcoding

**Decision**: The factory **registers** each deployed wrapper into the same registry the `010-universal-vaults` reader consumes (`services/agent/.../chain/vault_reader.py` + `apps/web/src/lib/chain/useVault.ts`), so a new wrapper appears in the app + `/admin/vaults` automatically, read through 010's **split** reader (the wrapper registers `abiKind:'sparkpoint'` and satisfies the SparkPoint superset by construction). 010 owns a **static-config** registry (`AddressBook.vaults[]`, no DB table); 011 owns the runtime `sparkpoint_wrappers` store the reader merges.

**Rationale**: 011 is the **execution/manage** half of the 010 **read/advisory** feature. 010 already generalized the reader from a single `config.vault_address` to a registry and shipped the **read-only** `/admin/vaults` state view (010 US3). 011 fills in the manage actions on that same page and the deposit/withdraw surface — so the two must share one registry. Because `SparkPointMorphoVault` exposes the same required methods (`previewDeposit/Redeem`, `convertTo*`, `totalAssets`, `asset`, `balanceOf`, `paused`, `performanceFeeBps`, `highWaterMark`, `feeRecipient`), the existing reader ABI reads it with no change (only `totalAssets`/`maxWithdraw` semantics differ internally, D3). No wrapper address is hardcoded in the frontend. **Rejected**: a separate 011 registry (would fork state from 010 and desync the admin page) or per-vault hardcoded addresses (unscalable, contradicts "launch new vaults later").

## D9 — Testnet has no ready Morpho vaults: self-create + seed for US2/US3 proofs

**Decision**: On Base Sepolia (84532, the alpha chain), `DeployMorphoVault.s.sol` **creates and seeds its own** test Morpho vault + market + oracle (Morpho Blue + the IRM / Chainlink-oracle-factory / MetaMorpho-V1.1-factory / Vault-V2-factory said to be on 84532) before deploying a wrapper against it. **Every Base-Sepolia Morpho address MUST be verified on-chain (`eth_getCode` / sepolia.basescan.org) before use — none is asserted here.** The widely-quoted VaultV2Factory `0x4501…5857` is in fact the **mainnet** address, and testnet Morpho deployment is not guaranteed, so `DeployMorphoVault.s.sol` MUST tolerate their absence (deploy the primitives it needs). Real curated vaults + the Morpho GraphQL API are **mainnet (8453) only**; testnet APY is on-chain-derived.

**Rationale**: There is no ready curated vault, yield, or API on testnet, so the fork/e2e proofs (partial-liquidity withdraw, non-rebasing accounting, V2 `max*==0`) require a controlled underlying we seed ourselves. Verifying the factory address on-chain avoids the documented mainnet-vs-testnet address trap. **Rejected**: mocking the Morpho vault entirely — a mock wouldn't exercise the real non-rebasing / partial-liquidity / V2 behaviours the invariants depend on; a seeded real Morpho market does.
