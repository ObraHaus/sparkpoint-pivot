# Changelog

All notable changes to **SparkPoint Pivot** are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

> **Status:** the **web app build has begun** (`apps/web`) — a faithful UI recreation of the approved design (every screen, shell, overlays, confirm gate, admin panel) on mock data; backend/agent/chain/auth + deployment are the next features. The Spec-Driven-Development planning artifacts and the design handover remain the source of truth. Build window: Jun 1 – Sep 4, 2026.

> **Note on this project:** SparkPoint Pivot is an **ObraHaus client product**, not part of the ObraHaus Apps Ecosystem. It is hosted in the ObraHaus GitHub org *for now* (ownership may transfer to the client later). It therefore **does not** use obrahaus-console SSO (it uses **wallet auth**), **does not** route AI through obrahaus-governor (it calls **Anthropic / an OpenAI-compatible API directly**), and uses its **own brand** (cobalt / gold / coral), not the OH Primary design system. These are sanctioned client-project divergences — see DEVELOPMENT.md.

- **Wallet-switch session binding now runs on every route (follow-up to the fix below)** — the account-binding lived inside `useSession()`, which is only mounted where the session is *consumed* (`/verify`, the deposit gate, the avatar-menu). So a wallet switch on a plain app route with no overlay open (e.g. `/portfolio`) wasn't caught: the previous wallet's session stayed live and the middleware kept admitting it until the next session-consuming page. A tiny always-mounted `SessionWalletBinder` (in `providers.tsx`) now keeps one `useSession()` instance alive app-wide, so the binding fires on any route. Caught by the new `wallet-switch` e2e (reverse case) running against live alpha; the injected wallet gained a deterministic "wagmi subscribed" signal so the switch can't race. Web-only. Web `tsc` / `eslint` / `node --test` green.
- **Switching wallets no longer strands an allowlisted wallet on "not in the alpha yet"** — the SIWE session (an httpOnly `sp_session` cookie carrying `{address, beta, admin}`) was minted once at sign-in and **never re-checked against the wallet actually connected**. So after signing in with a non-allowlisted wallet ("not in the alpha yet", correct) and then switching in the extension to an **allowlisted** wallet, `/verify` stayed stuck on the old wallet's verdict — `needsSignIn` was false (the session was non-null), so **no "Sign in with wallet" CTA appeared** and the good wallet could never get its own session; the route middleware likewise bounced it on the stale `beta:false` claim. The **reverse** was worse: signing in with an allowlisted wallet then switching to a non-allowlisted one let the new wallet coast into the app on the old `beta:true` claim. `useSession()` now **binds the session to the live `useAccount()` address**: when the connected wallet switches to a different account — or fully disconnects after having been connected — it clears the server session (`/api/auth/logout`) and re-fetches (→ signed-out), so the UI offers a fresh sign-in for the new wallet and the middleware stops honouring the old wallet's claim. Hardened with a de-duped logout across the multiple `useSession()` mounts and a `NetworkProvider` **disconnect watcher** (extension-initiated disconnects end the session too, not just the in-app Disconnect button); an SSR-reconnect guard avoids dropping a valid session before wagmi reconnects on load. **Non-custodial:** logout clears only the access cookie — never the wallet, keys, or funds, and `/exit` + `/trust` stay open (N2). Pure decision logic extracted to `session-binding.ts` with unit tests; the Playwright injected wallet gained account-switching + a `wallet-switch.spec.ts` covering both directions. Web-only — **no agent redeploy needed.** Web `tsc` / `eslint` / `node --test` green.
