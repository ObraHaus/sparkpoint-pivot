### Fixed (1110 — live Kamino withdraw validation)

- **Kamino withdraw no longer refuses real mainnet transactions.** The pre-sign validator had stale
  instruction discriminators: it used a non-existent kVault withdraw selector and only allowed the
  deposit-side farm bookkeeping. A real withdraw tx (verified by simulation) carries the kVault
  `withdraw` selector `b712469c946da122` plus the `unstake` and `withdraw_unstaked_deposits` farm

  recognised, the misnamed farm constants are corrected, and the strict account/amount checks

  unchanged. Unknown farm or kVault instructions are still refused. (`apps/web/src/lib/earn/kaminoLive.ts`)

### Added (079 — cross-chain Rhea / 071 Phase C review + gated live commit)

- **The 071 cross-chain Rhea rail now has a dual-access review and a reversible live slice.** This
  is the EVM-origin → Rhea (Burrow) on NEAR route through **1Click + Multichain Account (MCA)**;
  **078's same-chain NEAR → Burrow flow is separate**. `/vault`'s Rhea row and Sparky's Rhea earn
  card both link to `/vault/rhea-xchain`, which shows origin chain/asset/amount, the refund address,
  the MCA/`customRecipientMsg`, the one-time MCA fee, routing fee/net supplied and the supply APY.
  `dry=true` is the default and moves no funds. (`apps/web/src/lib/earn/xchain.ts`,
  `apps/web/src/components/vault/RheaXchainReview.tsx`,
  `apps/web/src/app/(app)/vault/rhea-xchain/page.tsx`,
  `apps/web/src/components/vault/EarnAcrossChains.tsx`,
  `apps/web/src/components/screens/chat/earn-quote-card.tsx`)
- **A live `dry=false` commit is server-gated and never signs.** It is refused (403) unless
  `EARN_LIVE_RHEA_XCHAIN` is exactly `"true"` AND the 1Click credential is present
  (`ONECLICK_API_KEY`; only its boolean presence is exposed, never the value). When allowed, it
  returns a live 1Click quote, the deposit address, and an **UNSIGNED** origin ERC-20
  `transfer(address,uint256)` plan for the user's own wallet. A first deposit needs one off-chain
  EVM `personal_sign`; without it the route returns `requiresSignature=true` + `messageToSign` and
  makes no 1Click call. The agent never signs, submits or broadcasts.
  (`services/agent/src/sparkpoint_agent/earn/rhea_xchain.py`,
  `services/agent/src/sparkpoint_agent/earn/service.py`,
  `services/agent/src/sparkpoint_agent/api/earn.py`,
  `services/agent/src/sparkpoint_agent/coordinator/chat_blocks.py`,
  `packages/shared/src/schemas/chat-block.ts`)
- **Withdraw is a guided review, not a transaction.** `/earn/rhea/xchain/withdraw` lists the
  documented Rhea SDK `relayer` / `nearMcaWithdrawTx` paths first and the Rhea app link-out only as
  the last resort, with sources, required wallet/chain and step-by-step copy. It states
  `nep413IsTransaction: false`, `custodian: null`, `signedBySparkPoint: false`, and says explicitly
  that a link-out is NOT a SparkPoint-signed transaction. No fake NEP-413-as-tx and no invented
  custodian. An unsigned in-app withdraw is not shipped because it needs a Rhea relayer credential
  we do not hold; inventing one would be dishonest.
- **Flags default OFF** (`EARN_LIVE_RHEA_XCHAIN`, `NEXT_PUBLIC_EARN_LIVE_RHEA_XCHAIN`); the page
  and the review-only agent routes 404 when both are off, and live `dry=false` is a 403 unless the
  server flag is on and `ONECLICK_API_KEY` is present. The browser validates the USDC amount and
  only enables the wallet confirm when the connected wallet and chain match the prepared plan.
  Tests use mocked 1Click transports only (no live quote, no funds).
  (`specs/079-rhea-xchain-mca/`, `docs/demo/079-rhea-xchain-mca.md`, `.env.example`)

### Added (078 — Rhea same-chain NEAR supply/withdraw, flags off)

### Added (NEAR-only login — 076)

- **A user can sign in with only a NEAR wallet, and MetaMask/EVM SIWE is unchanged.** The Connect page now offers a real "Sign in with NEAR" row (Meteor first, via the existing `@hot-labs/near-connect` adapter, no access key). The server issues a single-use nonce (stored in Postgres, 10-minute expiry), binds the canonical message to the app domain, verifies the ed25519 signature over the NEP-413 borsh payload (`tag = 2^31 + 413`), and checks via read-only `view_access_key` that the key is a **FullAccess** key of the account. The session cookie now records `{ chain: 'near' | 'evm', address }`; pre-076 cookies decode as `evm`, so live EVM sessions stay valid. (`apps/web/src/app/api/auth/near/*`, `apps/web/src/lib/near/{nep413,login,rpc,login-server,useNearLogin}.ts`, `apps/web/src/lib/auth/{session,useSiwe,session-binding,agent-status}.ts`)
- **Identity is chain-agnostic through the BFF and agent.** The BFF forwards `X-Auth-Chain` and the same owner string (a 0x address or a NEAR account id); the agent's `AccountContext` accepts a well-formed NEAR id when `X-Auth-Chain: near`, so chat, conversations, mandate, memory, allowlist and settings scope by the same owner key. EVM-only surfaces (vault quote/build and the execution spine) refuse honestly for a NEAR session, and portfolio/outcomes return an honest empty shell rather than an EVM read against a NEAR id. No existing table is dropped or rewritten. (`services/agent/src/sparkpoint_agent/api/{security,middleware,portfolio,vault}.py`, `services/agent/migrations/0045_near_login_nonces.sql`)
- **Env-gated CI/Playwright hook.** `NEAR_LOGIN_TEST_MODE=true` (server, never production) skips ONLY the on-chain key lookup, pinned to `NEAR_LOGIN_TEST_ACCOUNT`; the signature is still a real ed25519 signature over the NEP-413 payload made with a throwaway key generated at test time. No wallet file is read or copied. (`apps/web/e2e/pw/near-login*.ts`, `apps/web/src/lib/near/login-server.ts`)
- **The nonce endpoint validates config before minting.** `POST /api/auth/near/nonce` (was GET) checks the trusted recipient first, so an unconfigured deployment never leaves orphan nonce rows. (`apps/web/src/app/api/auth/near/nonce/route.ts`)
- **NEAR accounts are grantable in production.** Admin allowlist add/remove and access-application approve/deny now accept a NEAR account id (as well as a 0x address), and the admin Allowlist panel accepts `name.near`. Without this a NEAR user could sign in but never be added to the beta allowlist. (`services/agent/src/sparkpoint_agent/api/{allowlist,access,security}.py`, `apps/web/src/components/admin/AllowlistPanel.tsx`)
- **Defender hardening.** A NEAR account id that is shaped like a 0x EVM address is rejected on both the web and agent sides, so a registrable NEAR name can never alias an EVM owner key in the shared user store. Test mode now REQUIRES `NEAR_LOGIN_TEST_ACCOUNT` (an unpinned switch fails closed), and the NEP-413 recipient comes only from trusted env or the app's canonical domains — never an arbitrary request `Host` header. (`apps/web/src/lib/near/{account,login-server}.ts`, `services/agent/src/sparkpoint_agent/api/security.py`)
- **Tests.** Unit tests cover the verifier's valid/bad-signature/wrong-recipient/reused-nonce/expired/key-not-on-account cases and the session-binding rule for NEAR; the agent has middleware and nonce single-use tests; Playwright covers NEAR-only login reaching chat/portfolio/vault/settings and the EVM option remaining present. (`apps/web/src/lib/near/login.test.ts`, `apps/web/src/lib/auth/session-binding.test.ts`, `services/agent/tests/api/test_{near_auth,middleware}.py`)

### Fixed (NEAR implicit accounts — 076)

- **A NEAR destination can now be a 64-char lowercase hex implicit account.** The cross-chain recipient validator used the older `NEAR_RE` shape, which capped the id at 63 characters and so rejected implicit accounts — the default shape for many Meteor wallets. It now uses the 075 `isValidNearAccountId` rule (named ids OR exactly 64 lowercase hex chars), so a connected implicit account prefills and passes Continue, named accounts such as `sparkpoint2026.near` still pass, and uppercase / 63-char / `bad..near` ids still fail. The mirrored agent validator (`crosschain/addresses.py`) applies the same rule, so the confirm-time check agrees with the browser. `randomNonce()` now throws when `crypto.getRandomValues` is unavailable instead of returning an all-zero nonce, and the card's remaining `Date.now()` calls go through its injectable `nowMs()`. (`apps/web/src/lib/crosschain/address.ts`, `apps/web/src/lib/near/account.test.ts`, `services/agent/src/sparkpoint_agent/crosschain/addresses.py`, `services/agent/tests/crosschain/test_addresses.py`, `apps/web/src/lib/near/phaseC.ts`, `crosschain-quote-card.tsx`)

### Fixed (strict "X or Y?" choice allowlist — 2026-11-03)

- **Unlisted-verb commands no longer take the comparative path (Defender #349, scan 4cf8d0a).** `is_protocol_choice_question` now uses a strict allowlist: a no-amount two-venue turn is comparative only when it opens with an advice lead ("should I/we", "which", "what's better", "would you recommend", …) or when the whole message is a bare "venue or venue" choice with an optional short "for/on/with <asset>" tail. The old action-verb denylist and trailing-"?" question-shape fallback are gone, so "Add liquidity on Aave or Morpho?", "Close my Aave or Morpho position?", "Top up my Aave or Morpho position?" and "Moving my USDC from Aave to Morpho or leaving it?" keep their requested action on the planner path, while "Morpho or Aave?", "Rhea or Aave?" and "what's better, Morpho or Aave?" still get the comparison. The global `_ACTION_VERB_RE`, `has_financial_action_verb`, `_COMPARATIVE_RE`, the better/worse-than path and DAG routing are unchanged. (`services/agent/src/sparkpoint_agent/coordinator/guidance.py`, `tests/coordinator/test_comparative_questions.py`)

### Fixed ("X or Y?" protocol choice questions — 2026-11-02)

- **Choice requests and the verb “compound” no longer take the comparison (Defender follow-up 2).** The choice detector now uses a local action vocabulary that includes bridge, earn, farm, yield-farm, provide liquidity, restake, wrap/unwrap, rollover/roll over, park, shift, switch, migrate, zap and ape, and recognises request openers (“can/could/will you”, “I want”, “help me”, “let’s”, …) and “please” as actions that keep the planner. “compound” is a venue only as a noun: “Should I move to Aave or compound my earnings?” now has one venue and stays on the planner path, while “compound or aave?” is still a comparison. ### Fixed (streaming safety guard — 073, 2026-11-01)

- **Guarded prose can no longer be painted before the guard rejects it.** On beta (2026-10-30 00:31 PHT) `SPARKY_STREAMING=1` painted ~500 characters of a `"Morpho vs Aave"` answer, then the terminal meta guard rejected the COMPLETE answer and the code fallback replaced it — so users saw text the guard had already discarded. The old 059/063 stream only checked the first 40 characters and forwarded every later chunk unchecked; whole-answer checks (refusal, `is_unusable`, comparative servability/decline, `_clamp`) only ran at the end. A new pure, incremental `agents/stream_guard.py` (`StreamGuard`), shared by `Sparky.stream_reply` and `Literacy.stream_tip`, releases only COMPLETE segments: sentence terminators (`. ! ?` followed by whitespace/end, excluding decimals and `e.g.`/`i.e.`/`vs.`) or a newline. With no boundary in 280 characters it releases up to the last whitespace while keeping a 64-character lookbehind tail, so a multi-word guard phrase cannot be split across released/unreleased text. Every release checks the CUMULATIVE text with the SAME action/meta predicates as the final block, so a phrase completed by a later chunk trips before it is painted. On a trip the guard stops releasing, the model iterator is closed early (`aclose` in `finally`), and the terminal reply keeps the exact 065 failure reason (`meta`/`action`), so 066/067 retry and comparative-fallback behaviour is unchanged. If anything had already been painted, one **retract** is emitted as an empty `text-delta` under a fresh `streamId` (`general-<n>-r` / `tip-<n>-r`); the web reducer already resets on a new stream id, so no new event type or client logic was needed. Release is clamp-aligned (`StreamGuard.finish`), so a served final block never shrinks below what was painted. (`agents/stream_guard.py`, `agents/sparky.py`, `agents/literacy.py`, `agents/guard_text.py`, `coordinator/dag.py`, `apps/web/src/lib/chat/streamText.ts`)
- **Comparative answers are held WHOLE while streaming.** Their acceptance depends on whole-answer checks that cannot be known mid-stream (every subject named, not a whole-answer refusal/decline), and the beta incident was exactly that turn shape. `HOLD_COMPARATIVE_PROSE = True` in `stream_guard.py` means no prose delta is emitted for a comparative turn; the terminal `text` block (served answer or code fallback) is the first prose the user sees, while tool-step progress still streams. This is a policy constant, not a new env flag; `SPARKY_STREAMING` and every deploy env are unchanged.
- **TTFT trade-off measured offline.** `scripts/stream_guard_bench.py` drives the real `Sparky.stream_reply` with a fake 4-char/25 ms model: normal prose paints after one complete sentence (0.51 s vs the old 0.25 s 40-char window on a ~450-char answer), a long first sentence is bounded by the 280-char cap (1.79 s), and a comparative turn paints nothing (`specs/073-streaming-guard/research.md`).
- **Regression tests:** guard unit rules (decimals, abbreviations, newline, cap+tail, cross-segment match, action, sticky trip, clamp); Sparky/Literacy fake-model tests proving the guarded phrase never appears in a delta, the stream is aborted early, and retract only happens when something was painted; a real uvicorn `/chat` + SSE e2e that iterates EVERY `_META_SHAPED`/`_ACTION_SHAPED` example across general and tip turns, asserts no prose delta at all for comparative turns (served and fallback), and a clean answer paints before `done` and reconciles with the final block; the old 40-char expectations in 059/063 tests now encode sentence gating. Fail-open: a failed run writes only the failure state — the last good list and pick keep serving. A daily loop plus a 5-minute poll for admin "Run now". Pinned by 27 `node:test` units (live-verified: 4663 → 0 vaults, 8453 → 100 discovered / 13 accepted / deterministic pick).
