> **Note on this project:** SparkPoint Pivot is an **ObraHaus client product**, not part of the ObraHaus Apps Ecosystem. ### Added (024 Phase 3 — the web **read path** for a Vault V2, which is a different contract, not a variant)
- **`useVault` now selects its read set by vault kind, via a THIRD predicate.** `isWrapper`, `feeBasis` and the new `isFeeWrapper` answer three different questions — "may I call the SparkPointMorphoVault-only views?", "which fee copy is honest?", and "which ABI and which reads?" — and collapsing any two of them is how a reverting read or a wrong fee string reaches production. `isWrapper` is deliberately left untouched: its exclusion of `morpho_fee_wrapper` is correct, because `label()`/`morphoVault()`/`factory()`/`isSparkPointVault()` all revert against a V2.
- **New `morphoVaultV2Abi` (web-local and leaf, with `wadToBpsCeil`).** `@sparkpoint/shared/abis` is auto-generated from *our* contracts and a Vault V2 is Morpho's, so there is no artifact to export from; the precedent is `useVault`'s existing inline `morphoWrapperViewsAbi`.
- **The three bugs this prevents — each of which would have shipped a *plausible wrong number* rather than an error:**
  - **A fabricated 10% fee.** `useReadContracts({allowFailure: true})` resolves a selector a V2 lacks to `undefined` instead of throwing, and an `undefined` `performanceFeeBps` falls straight through to the policy default of **1000** inside `netApy`. The launch read set pointed at a V2 would therefore display a confident 10% fee that was never read from the vault — whose real fee is **0**. The launch-only reads (`paused`, `performanceFeeBps`, `MAX_PERFORMANCE_FEE_BPS`, `highWaterMark`, `feeRecipient`) are now `enabled`-gated **off** against a V2, and the V2's own WAD-scaled `performanceFee()`/`managementFee()` are read instead and converted with exact-integer, round-**up** `bigint` arithmetic. `wad * 10000` reaches 1e22 for a 25% fee — the same conversion in the FR-020 gate's shell version wrapped that to **−8 bps** and passed a 0-bps ceiling.
  - **A 1e12 mis-scale.** A V2's own `decimals()` is **18** while its asset is 6-dp USDC. `assetDecimals` now comes from `asset()`'s own `decimals()`, with a new separate `shareDecimals` for share amounts. Unfixed, 100 USDC would render as ~0.0000000001 and the USD valuation would collapse to zero, dropping the position out of net worth. The existing invariant comment in this file predicted this break by name.
  - **An approve on the wrong token.** New `depositToken` follows the **vault's** `asset()`, not the chain's `usdc`. On Base Sepolia those differ (Circle's vs Aave's, both `symbol() == "USDC"` at 6 dp). Unfixed, the user would sign a perfectly successful approve on a token the vault never pulls and the deposit would then revert on-chain — the worst shape of failure, because the approve looks like it worked.
- **`max*` are omitted from the V2 ABI entirely and `enabled`-gated off**, rather than merely "not used". On a V2 they are `pure returns (0)` and are not enforced inside `deposit`/`withdraw`; a UI that trusts them tells a holder **"you cannot withdraw"** — false, and the single worst thing to say to someone trying to exit (N2). Consumers fall back to the policy caps instead of a fabricated limit.
- **`retired` now scans BOTH address-book lists.** A V2 lives in `morphoFeeWrappers`, and this hook's own header records that a per-call-site `retired` flag was forgotten once and Defender caught a live deposit bypass via `/confirm/[intent]`. A vault invisible to the scan re-opens exactly that class of bug.
- `maxPerformanceFeeBps` on a Fee Wrapper comes from **policy constants, never a vault read** — a V2 has no such selector and its own ceiling is 50%, so the ≤20% figure is a policy commitment (Safe owner + ≥3-day timelock), which is what `feeCapEnforcementLabel(feeBasis)` already tells the user.
- **11 new tests** covering the WAD overflow (including the exact 25%-fee case that broke the shell version), round-up-not-truncate at the 20% cap, the deliberately-absent selectors, the `max*` omission, and that the N2 exit surface is present and unmutated.

### Changed (024 Phase 3 — the deploy script is now **idempotent and resumable**, which is what finished it)
- **It took four attempts. All three failures were the same root cause — RPC view lag — and none was a logic error;** each aborted safely rather than building on uncommitted state. Recorded because the next chain deploy will meet them again: (1) `createVaultV2` committed with status 1 while the immediate `factory.vaultV2` view returned **empty**, leaving the vault created and the salt spent; (2) `setCurator` was **mined** yet the pending-nonce view still counted it in-flight, so the next send reused the nonce and was rejected as an underpriced replacement; (3) `exec absCap(market)` failed **gas estimation** with `TimelockNotExpired` even though that selector's timelock was 0 and the submit had a receipt — the estimator ran against a state view predating the submit, where `executableAt` reads 0, and V2 reverts `TimelockNotExpired` for 0 exactly as for "not yet due".
- **Fixes, each aimed at the class rather than the instance:** every step is guarded by a read of the state it produces (`tl_if`/`tx_if`), so a re-run skips completed work instead of reverting — `addAdapter` on a known adapter and `increaseAbsoluteCap` to an equal value both revert, so re-running was previously *worse* than wasteful. The script now **owns the nonce** (read once, passed explicitly, incremented on each confirmed receipt) instead of trusting a view that demonstrably lags. View reads retry (`read_view`) — the adapter read-back had **no guard at all** and a lagging read there would have carried an empty address into the cap-id pre-images. `await_executable` asks the vault itself before every exec. A submitted-but-unexecuted action is **adopted** rather than re-submitted, because re-submitting identical calldata reverts `DataAlreadyPending` (`0xd91ff208`). Every step prints its tx hash — the first failure discarded it and the created vault had to be recovered by hand.
- **The one-shot dead deposit's done-check deliberately precedes its `previewMint` assertion.** Once `0xdead` holds the shares the vault is no longer empty, so `previewMint(1e18)` need not still equal exactly `1000000`; asserting first would abort an already-finished deployment at a false failure and invite a re-mint. Ask "is it already done?" before "is it safe to do?".
- **Rehearsing each resume against a fork of the *then-current* live block** — not a stale fork — is what caught failure (3) and `DataAlreadyPending` for free, before they cost a live transaction.
- **Corrected count: the sequence is 52 transactions, not 43.** Nonce 67 → 119 confirms it (step 3's nine `tl()` pairs alone are 18). Total cost: exactly **1.000000 USDC** and **0.0000616 ETH** of gas.

### Changed — HONESTY (024 **T024**, a ratified obligation that gates any Fee Wrapper deposit)
- **The performance-fee disclosure is now keyed on how the fee actually accrues, not hard-coded to a high-water mark.** Ratifying v3.0.0 carried a *disclosure* obligation, not merely a wording tweak: a Morpho Vault V2 keeps **no high-water-mark state at all** (`interest = newTotalAssets.zeroFloorSub(_totalAssets)`), so a gain **following an earlier loss IS charged** even while the holder is below their previous peak. SparkPoint's own vaults *do* hold a real `_highWaterMark` (confirmed in `SparkPointVault.sol` — `accrueFee()` returns 0 when price-per-share ≤ the mark), so today's copy is accurate and this is a **conditionalisation, not a correction**. New `VaultFeeBasis` (`high_water_mark` | `per_period_gain`) is derived **centrally** from the vault kind — `lib/policy/feeCopy.ts` + `useVault().feeBasis` on the web, `policy/fee_copy.py` on the agent — and never decided per call site, because a forgotten per-site flag is exactly how the retired-wrapper deposit bypass reached production and had to be caught by Defender.
- `PERFORMANCE_FEE_DISCLOSURE` is retained **byte-identical**, so 015/FR-006 verbatim parity with the agent's `_DEPOSIT_DISCLOSURE` still holds and today's `/vault/quote/*` wire output is unchanged (pinned by tests on both sides). `performanceFee.base` gains a second value `period_interest_no_hwm`, and `performanceFee.highWaterMark` becomes **nullable** — a Vault V2 has no `highWaterMark()` selector, and writing `"0"` would read as "the mark is at par", a materially different promise from "no mark exists".
- **Sites the task list did not name, found by audit and also fixed:** the **withdraw receipt note** (`vaultConfirmModel.ts`) asserted "over your high-water mark" in *both* branches; the assistant's canned `what_is_a_performance_fee` answer (`agents/literacy.py`) asserted it unqualified with no vault context available, and is now scoped to the vault it is true of; `NonCustodyBadge.tsx` called the 20% fee ceiling "**immutable — governance can never exceed it**", which v3.0.0 explicitly downgrades to a policy commitment (Safe owner + ≥3-day timelock) on the Fee Wrapper path, since Morpho's own V2 ceiling is 50%. `/fees` had its high-water-mark claims **scoped to the launch vault** it actually reads, rather than stated universally; it deliberately does **not** describe a Fee Wrapper, because none is deployed and advertising one would fabricate a capability (Principle III).

### Added (024 **T034 / FR-020** — the child-vault eligibility check is now an enforcing CI gate)
- **`contracts/script/vault-eligibility-check.sh` + `.github/workflows/vault-eligibility.yml`.** Before a Fee Wrapper may bind to a third-party Vault V2, that child must pass an automated on-chain check — `abdicated(bytes4)` is a public mapping and `isVaultV2` a public factory view, so this is fully automatable and therefore a gate, not a checklist. Per candidate: `factory.isVaultV2`, the **three critical gate setters permanently abdicated** (the one real N2 hole in wrapping someone else's vault — a live gate lets the child's curator block the exit path), `asset()` match (a check our own factory never performed), and native fee ceilings for the NET stacked-fee disclosure (IV.5). Modelled on the `policy-parity` pair: all logic in a committed, locally-runnable helper; green-by-skip **only** when a chain has no declared candidates.
- **Read-only by construction, and safe to point at mainnet** — `cast call` only, never `cast send`, no signing key in the job env. It *must* read mainnet: every candidate lives on Base 8453 or Robinhood 4663, because Base Sepolia has no third-party Vault V2 to wrap at all. No RPC secret is required; each chain declares a public fallback and the script verifies via `cast chain-id` that the endpoint really serves that chain before trusting a read, so a wrong endpoint fails closed instead of reporting a false PASS.
- **Verified live:** all three D2/D3 candidates PASS — Steakhouse Prime USDC and Gauntlet USDC Prime on 8453, Steakhouse USDG on 4663 — using public RPCs with no secrets. **Negative paths proven to FAIL:** a wrong expected asset, a non-Vault-V2 address (Morpho Blue), a tampered selector, and a real 25%-fee vault against a 0-bps ceiling. Gate selectors were **recomputed with `cast sig`** rather than trusted from docs, and the script re-derives them at runtime so neither the script nor the candidates file can be silently wrong.
- **An overflow bug the negative test caught before it shipped:** `wad * 10000` for a 25% fee is `2.5e21`, which wraps in bash's 64-bit signed arithmetic to **−8 bps** and *passed* a 0-bps ceiling — i.e. the gate would have silently admitted a 25%-fee vault. Arithmetic moved to `python3` and rounded **up**, so a fee a hair above a ceiling fails rather than truncating into a pass.
- **The FR-020 liquidity floor is deliberately NOT asserted, and the script says so.** Withdrawable liquidity on a Vault V2 is idle assets *plus* what each Blue market can currently pay out, which needs Morpho's indexer; a naive on-chain `asset.balanceOf(vault)` is worthless for it — verified: Steakhouse Prime USDC holds **$567M of `totalAssets` and exactly 0 idle**, so an idle-ratio floor would read 0% for a perfectly healthy vault and reject every candidate. The declared ratio is carried as allowlist evidence and enforced pre-signature in the UI. The gate never passes a check it did not perform.

### Added (024 **T032** — registry-backed vault resolution, behind a flag, fail-open)
- **The 0026 registry now sits in front of the single `SPARKPOINT_VAULT_ADDRESS` read**, gated by `SPARKPOINT_VAULT_REGISTRY_ENABLED` (default **off**). Flag off ⇒ the env value verbatim with **no database round-trip**, so enabling the registry later cannot add a failure mode or latency to today's path. Flag on ⇒ the chain's live `first_party` row. Flag on but the registry is unmigrated, unreachable or has no row ⇒ **fall back to the env value**, warning once per chain.
- That fallback is load-bearing, not laziness. A registry miss means "the registry does not know", never "there is no vault" — `0026` is additive and is **not applied** on develop. Failing closed would take a funded, working vault offline because a *display* table was empty, which is precisely the SparkPoint-side block **N2** forbids. An ambiguous registry (two live `first_party` rows) logs an error and still serves the oldest row deterministically rather than refusing.
- **IV.5(d) policy isolation is structural:** the resolver returns a bare address string — the exact shape `AgentConfig.vault_address` already had — so no row content (label, fees, status, vetting notes) can reach `PolicyModule`, `SessionKeyValidator` or a strategy-direction path.
- **One resolution per request.** `VaultReader` gains a `vault_address` property, and `/build-tx` plus both `/vault/simulate/*` now take the vault from the reader instead of re-reading the config. `/build-tx` previously read the env var a *second* time; once the registry can override it, the two reads could straddle an operator's edit and price a quote against one vault while emitting calldata for another.
- New `db/vault_registry.py` (reads for all three 0026 tables + the APY-snapshot insert Phase 4 needs) and `GET /admin/vault-registry`, the read-only/advisory surface Phase 2 calls for. It returns `available: false` with a reason rather than 500ing on an unapplied `0026`, and reports `resolutionEnabled` so an operator can see that rows exist while the service still resolves from the env var. Mounted at `/admin/vault-registry`, **not** `/admin/vaults/registry`, because `GET /admin/vaults/{vault}` is a catch-all declared below it and FastAPI matches in registration order — that path would have been silently shadowed into a lookup for a vault named "registry".
- **Known limit, recorded rather than glossed:** the one-vault assumption is deeper than the env read. `PgVaultFlowStore` is still constructed with a single `vault_address` and stamps it on every `onchain_events` row, so registry resolution alone does **not** make portfolio/PnL multi-vault.

Those two, plus the pre-existing `sendTransaction`-without-`chainId` gap a selector would make reachable, are documented as Phase 5/6 work rather than half-built.

### Fixed (021 phase 2 — poller hardening from an adversarial review: anti-spam, idempotency, coverage)

### Fixed (021 phase 2 — new-recommendation alert made deterministic; no LLM-jitter false positives)
- **Live-caught in first-boot validation:** the proactive new-recommendation poller keyed off the
  recommender's *top* rec, but the recommender's candidate ordering is LLM-generated and jitters
  run-to-run (the US5/T010 finding), so re-scoring the same wallet twice produced two different keys
  and fired a spurious "new recommendation." Re-keyed on the **sorted SET of policy-cleared strategy

### Changed (020 — US5 follow-up: the signed-tx relay self-heals a briefly-lagging tx)
- **A signed transaction now reliably correlates to its outcome even when the chain is a beat behind.**
  The ExecutionDrawer's best-effort relay to `POST /submit-signed-tx` (which the #91 hardening made
  verify the tx on-chain **before** recording) previously fired *before* the receipt confirmed and
  ignored the response — so a not-yet-visible tx got a `409 DATA_STALE` and was never recorded,
  silently losing the per-recommendation outcome correlation. The relay now fires **only after the
  receipt confirms** (the tx is retrievable on-chain, matching #91's design) and **retries a `409

  permanent and never retried, and a **reverted tx is never relayed**. Non-custody preserved (N2): the
  relay is fire-and-forget, never blocks the sign / confirm / exit flow, and the direct on-chain
  receipt is the source of truth. The pure retry policy is extracted to
  `executionModel.relayWithRetry` (+6 web unit tests, 146 total). Web-only; no migration.

### Security (019/020 — /submit-signed-tx verifies the relayed tx before recording it)
- **A signed-transaction relay is now recorded only after it's verified on-chain.** `POST /submit-signed-tx`
  previously byte-matched the relayed `txHash` against the issued bundle **best-effort** — and *skipped*
  the check entirely when the tx wasn't retrievable, recording the execution anyway
  (`orchestrate.submit_signed`). A bogus, mistaken, or not-yet-propagated `txHash` therefore created a
  **phantom `executions` row** that could mis-attribute a US5 outcome (surfaced during the SC-010
  live-validation, when a client mistakenly relayed a log-topic hash instead of the tx hash). The relay
  now **requires** the tx to be retrievable on-chain **and** to byte-match the issued step before it
  records anything: a hash we can't retrieve (after a short bounded retry that absorbs RPC propagation
  lag — the drawer relays only *after* the wallet confirms the receipt) returns a **retryable
  `DATA_STALE`** with **no row**; an RPC outage while verifying returns a retryable `UPSTREAM_UNAVAILABLE`;
  a byte-mismatch stays `VALIDATION_ERROR`. Non-custody preserved (N2): rejecting the correlation relay
  never gates the user's funds — the transaction is on-chain regardless, and the client re-relays once it
  propagates. +2 agent tests (714 total); the replay-dedup test now verifies through a retrievable tx. No
  migration; takes effect on the agent redeploy.

- **Live chat deposit recommendations no longer render as "couldn't be verified"** — the agent attached knowledge (Obsidian) citations with a **date-only** `asOf` (e.g. `2026-07-14`) or an empty string, but the shared `Citation.asOf` schema is strict ISO-8601 (`z.string().datetime()`, `Z`-suffixed), so every recommendation block carrying a citation failed validation and the web fail-closed it to an inert *"This response couldn't be verified and can't be acted on."* card. The agent now normalizes `asOf` to a `Z`-suffixed UTC datetime at the source (`services/agent/.../knowledge/search.py` — date-only frontmatter expands to midnight UTC; absent/unparseable falls back to now). The chat portfolio provider now surfaces idle wallet USDC as its own **"Wallet (idle)"** position row (single source of truth — the same read that feeds net worth), so the card and the summary agree. Chat-only (the REST `/portfolio` API keeps its vault-only positions + separate `idleUsdc`). Agent ruff / mypy / pytest green. **Requires an agent-service redeploy to take effect.**
- **Wallet-switch session binding now runs on every route (follow-up to the fix below)** — the account-binding lived inside `useSession()`, which is only mounted where the session is *consumed* (`/verify`, the deposit gate, the avatar-menu). So a wallet switch on a plain app route with no overlay open (e.g. `/portfolio`) wasn't caught: the previous wallet's session stayed live and the middleware kept admitting it until the next session-consuming page. A tiny always-mounted `SessionWalletBinder` (in `providers.tsx`) now keeps one `useSession()` instance alive app-wide, so the binding fires on any route. Caught by the new `wallet-switch` e2e (reverse case) running against live alpha; the injected wallet gained a deterministic "wagmi subscribed" signal so the switch can't race. Web-only. Web `tsc` / `eslint` / `node --test` green.
- **Switching wallets no longer strands an allowlisted wallet on "not in the alpha yet"** — the SIWE session (an httpOnly `sp_session` cookie carrying `{address, beta, admin}`) was minted once at sign-in and **never re-checked against the wallet actually connected**. So after signing in with a non-allowlisted wallet ("not in the alpha yet", correct) and then switching in the extension to an **allowlisted** wallet, `/verify` stayed stuck on the old wallet's verdict — `needsSignIn` was false (the session was non-null), so **no "Sign in with wallet" CTA appeared** and the good wallet could never get its own session; the route middleware likewise bounced it on the stale `beta:false` claim. The **reverse** was worse: signing in with an allowlisted wallet then switching to a non-allowlisted one let the new wallet coast into the app on the old `beta:true` claim. `useSession()` now **binds the session to the live `useAccount()` address**: when the connected wallet switches to a different account — or fully disconnects after having been connected — it clears the server session (`/api/auth/logout`) and re-fetches (→ signed-out), so the UI offers a fresh sign-in for the new wallet and the middleware stops honouring the old wallet's claim. Hardened with a de-duped logout across the multiple `useSession()` mounts and a `NetworkProvider` **disconnect watcher** (extension-initiated disconnects end the session too, not just the in-app Disconnect button); an SSR-reconnect guard avoids dropping a valid session before wagmi reconnects on load. **Non-custodial:** logout clears only the access cookie — never the wallet, keys, or funds, and `/exit` + `/trust` stay open (N2). Pure decision logic extracted to `session-binding.ts` with unit tests; the Playwright injected wallet gained account-switching + a `wallet-switch.spec.ts` covering both directions. Web-only — **no agent redeploy needed.** Web `tsc` / `eslint` / `node --test` green.
