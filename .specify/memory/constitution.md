# SparkPoint Pivot Constitution

SparkPoint Pivot is "The First AI-Native Onchain Hedge Fund": a fully self-custodial, chat-based Personal DeFi Assistant paired with an AI-managed Aave Yield Vault, launching on Base with Sui as the designated fast-follow network and a fully self-custodial bridge between them. The AI is the fund manager, but a deterministic policy layer means the model never holds final execution authority — the user signs every transaction. This constitution governs how the project is specified, built, and shipped. It learns your goals, explains every move, proves every result onchain, and never touches your keys.

## Core Principles

### I. Non-Custodial by Construction (NON-NEGOTIABLE)

Native non-custody is the product's foundation, not a feature. The five non-custody invariants MUST hold in every design, contract, and agent behavior, and no code path may violate them:

- **N1 — No admin withdrawal.** Only the user can move funds to an external address. The protocol and agents MAY direct strategy within an on-chain allowlist but MUST NOT have any code path that withdraws user funds to a SparkPoint-controlled address.
- **N2 — Withdraw-always escape hatch.** The user MUST be able to exit directly on-chain (redeem vault shares, withdraw from Aave) even if SparkPoint's frontend and agents are entirely offline, on EVERY supported network. The kill-switch MAY pause new deployments but MUST NEVER block user withdrawals. This is PROVEN today on Base (ERC-4626 self-service redeem, backend-independent); on Sui it is a **design requirement** the follow-on Sui (non-EVM / Move) custody increment MUST satisfy before the Sui withdraw-always claim is treated as demonstrated (see "Proof status of withdraw-always / self-custody" below).
- **N3 — User-owned keys.** The user MUST be the sole owner/admin signer of their smart account. The system MUST NOT generate or hold custody of user wallets. Default execution mode is per-action user signature.
- **N4 — Scoped, instantly-revocable, time-boxed automation.** Opt-in automation MUST use an ERC-4337 session key bounded by the on-chain PolicyModule (allowlisted vaults only, per-tx and cumulative caps, max slippage, hard expiry). The user MUST be able to revoke instantly and unilaterally without SparkPoint's cooperation. A compromised agent MUST NOT be able to exceed its on-chain scope.
- **N5 — Bounded, verifiable custody semantics.** The vault MUST be single-purpose. Code is immutable by default; a wrapper admitted under IV.5 MAY be upgraded **only** through a TimelockController-owned beacon (3-of-5 proposer, independent canceller, ≥72h delay) whose upgrade path is never an asset path and never gates withdrawals. Multisig/timelock govern PAUSE and bounded parameters, never fund movement. The Trust Center MUST surface exact on-chain permissions — including the upgrade authority — so non-custody is provable, not promised. **(v4.0.0)**

The non-custody invariants hold on EVERY supported network, and the cross-network bridge is fully self-custodial: the user signs the lock/burn on the SOURCE network, receives funds in their OWN wallet on the DESTINATION network, and SparkPoint NEVER custodies funds in transit. Bridge actions pass the same single pre-trade simulation, guardrail checklist, and you-sign gate as swaps and deposits; per-network and per-bridge caps wire to the on-chain policy limits.

**Proof status of withdraw-always / self-custody (Base proven, Sui a design requirement).** Withdraw-always (N2) and the self-service self-custody exit are PROVEN today on Base (ERC-4626 redeem + the prove-it permissions read, backend-independent). On Sui they are a **design requirement** that the follow-on Sui (non-EVM / Move) custody increment MUST satisfy before the Sui self-custody claim is treated as demonstrated — the Sui self-service exit path and permissions read are to-be-designed. The product commits to fully-self-custodial parity on Sui; it is a commitment pending that increment, not a shipped Base-equivalent proof.

Any proposed change that touches custody semantics MUST be rejected by default and requires explicit re-ratification under Governance before it can proceed.

### II. AI Proposes, Deterministic Policy + User Disposes (NON-NEGOTIABLE)

The model is an advisor, never an authority. AI agents (portfolio reader, strategy recommender, executor, vault manager, guardrail/policy agent) MAY analyze, rank, and propose actions. A deterministic policy layer MUST validate every agent output before any execution path is reachable; output failing policy MUST be rejected, never "best-effort" executed. Every state-changing transaction MUST be signed by the user, with per-action signing as the default. The only exception is scoped session-key automation, which remains bounded by the on-chain PolicyModule (Principle I, N4). AI reasoning runs on a large language model reached through an OpenAI-compatible gateway (provider-swappable; currently OpenRouter behind a self-hosted LiteLLM proxy), but the model's output MUST NOT reach the chain without passing the deterministic policy layer and the applicable user-signing or session-key constraint. AI hallucination MUST NOT be able to cause an unauthorized or out-of-policy transaction.

### III. Provable, Not Promised

Trust is earned on-chain, not asserted in marketing copy. Realized results and current permissions MUST be reconstructable from on-chain data. Yield MUST be reported honestly and net of everything (fees, costs, slippage); the launch vault is 0-management / profit-only performance-fee (0 management fee, 0 fee on principal, capped (≤20%) high-water-mark performance fee on realized yield, default 10%, fully disclosed), and yield MUST come from the underlying protocol (Aave v3), never from token incentives. The product MUST NOT lead with return projections or promise specific future returns. Any figure shown to users MUST be current and verifiable, and each strategy recommendation MUST be labeled over time with its realized PnL (outcome logging). The Trust Center MUST display the exact on-chain permissions granted, so users can independently confirm the non-custody invariants.

### IV. Security & Bounded Blast Radius

Every component MUST be designed so that the worst-case outcome is contained. The six guardrails are mandatory and MUST all be present at launch:

1. The deterministic policy layer wraps every AI decision (the model never has the final word).
2. Hard caps MUST be enforced on-chain: per-user TVL cap, total protocol cap, and vault deposit cap.
3. A multisig kill-switch MUST exist that is PAUSE-ONLY — it halts new deployments and MUST NEVER block user withdrawals.
4. A pre-trade simulation MUST be previewed to the user before they sign (provider-neutral — the mechanism is a simulator, e.g. a self-hosted fork, not a specific vendor).
5. Only whitelisted protocols are permitted. Aave v3 and Aerodrome are fixed and un-addable — interaction with any protocol outside this whitelist MUST be impossible by construction. In addition — for branded wrapper vaults ONLY — Morpho vaults drawn from an on-chain **curated Morpho allowlist** of vetted Morpho vaults are permitted, and their admission is construction-enforced: (a) each wrapper's single underlying Morpho vault is bound **at initialization, immutably and with no setter**, never re-pointable, re-targetable, or swappable thereafter — a proxy upgrade may not re-point it (enforced by review + CI); the SparkPointVaultFactory MUST verify curated-allowlist membership of that target at deploy time and REVERT otherwise; no wrapper consults a mutable registry at runtime — a deployed wrapper's reachable protocol set is frozen (impossible by construction at the instance level). **(v4.0.0)** A wrapper MAY be upgradeable, but ONLY under the IV.5/v4.0.0 rule: a TimelockController-owned beacon (3-of-5 proposer, independent canceller, ≥72h delay), no EOA, and withdrawals never gated by a pending upgrade. (b) Additions to and removals from the curated allowlist are governed by the SAME multisig + timelock that governs the PAUSE kill-switch, with a mandatory timelock delay and guardian veto window (no single key may add an entry); they take effect for FUTURE deployments only and MUST NOT alter custody or block the withdraw path of any already-deployed wrapper. (c) A Morpho vault is INELIGIBLE if any SparkPoint-controlled address holds an owner, curator, allocator, guardian, timelock-admin, or withdrawal role over it, or if its curator may reallocate to arbitrary/unbounded markets absent continuous monitoring and an enforced removal path. (d) The curated allowlist is a SEPARATE on-chain registry consumed ONLY by the SparkPointVaultFactory at deploy time — it MUST NOT be readable or consulted by the PolicyModule, the SessionKeyValidator, or any agent/session-key strategy-direction path, and Morpho MUST NOT be a target of agent strategy direction or the user-signed swap path. This extends pause-only governance by exactly one narrowly-scoped, timelocked, deploy-time-only admission action and nothing else.
6. Every vault — the launch Aave Yield Vault and each factory-deployed wrapper instance — MUST be bounded and single-purpose. Upgradeability is permitted ONLY under the IV.5/v4.0.0 wrapper rule (a TimelockController-owned beacon; no upgrade may alter the child, the fee cap, or the withdraw path). **(v4.0.0)**

All smart contracts MUST keep a simple, auditable surface and MUST have unit and fuzz tests before mainnet. Complexity that widens the blast radius MUST be justified or removed.

### V. Conservative, Transparent Launch

The launch is deliberately narrow and honest. The launch DEFAULT vault MUST be a single conservative Aave Yield Vault (ERC-4626) with a 0 management fee, 0 fee on principal, and a capped (≤20%), profit-only, high-water-mark performance fee on realized yield (default 10%), fully disclosed and non-custodial: deposit USDC, earn Aave yield, withdraw anytime, non-upgradeable. We only earn when you earn — never on your principal, never by taking custody. The fee recipient is a non-privileged share holder, and the performance fee NEVER touches principal or the withdraw path; feeRate is the only mutable param (timelocked, hard-capped), never altering custody. The SRK token MUST be non-essential to core vault function — the vault MUST work fully without SRK, which activates a later cycle. The product MUST NOT offer token-incentive yield, leveraged strategies, or any product that contradicts the conservative posture at launch. New strategies MUST NOT be added under the banner of the launch vault.

**Curated Morpho-wrapper vaults (ratified v2.0.0).** In addition to that conservative Aave Yield Vault — which REMAINS the launch default, single-purpose and unchanged — SparkPoint MAY operate a **deploy-only factory** (`SparkPointVaultFactory` / `SparkPointVaultFactoryV2`) that deploys branded, single-purpose ERC-4626 **wrapper vaults**, each supplying pooled USDC into **exactly one curated-allowlist vault bound immutably at initialization** (per IV.5). A wrapper is immutable **or** upgradeable strictly under the IV.5/v4.0.0 rule. **(v4.0.0)** No new strategy is bolted onto the launch Aave vault; each wrapper is a separate single-purpose vault. Every wrapper MUST preserve N1–N5 by construction, mirroring the launch vault:
- **N1 (no admin withdrawal):** no sweep/migrate/rescue/re-target path; the performance fee accrues ONLY to a non-privileged share holder, is realized by **minting shares** against yield, and NEVER touches principal or the withdraw path — no wrapper may transfer USDC out of the pooled position to a fee, treasury, or recipient address directly. 0 management fee, 0 on principal; the fee rate is the only mutable per-wrapper param (timelocked, hard-capped ≤20%, default 10%), never altering custody. **(v3.0.0)** On a `SparkPointMorphoVault` the fee is charged only above a share-price **high-water mark**. On a **Morpho Vault V2 Fee Wrapper** it is profit-only *per accrual* — never in a flat or falling period, always share-dilution, never on principal — but Vault V2 keeps **no high-water-mark state**, so a gain following an earlier loss IS charged even while the holder is below their previous peak. That difference MUST be disclosed in the user-facing fee copy for a Fee Wrapper; the "above a high-water mark" phrasing MUST NOT be used for one.
- **N2 (withdraw-always):** wrapper redemption is permissionless and MUST NOT be gated, delayed, or blocked by any SparkPoint-held key, role, or pause (the guardian pauses DEPOSITS ONLY, never withdrawals), with no lock-up. Exit is best-effort against the underlying vault's available liquidity; **insufficient underlying Morpho liquidity is the SOLE permissible cause of a partial or delayed exit — SparkPoint can never be that cause.**
- **N3 / N4 (user keys; scoped automation):** deposits and withdrawals are user-signed; any session-key access to a wrapper is bounded by the on-chain PolicyModule exactly as for the launch vault — no session key gains implicit authority over a wrapper by virtue of the factory deployment.
- **N5 (bounded, single-purpose; v4.0.0):** each wrapper is single-purpose with exactly one child; the permitted shapes are an immutable full-bytecode contract **or** a `BeaconProxy` behind a TimelockController-owned beacon (IV.5/v4.0.0). A proxy may never re-point its child, and no upgrade may introduce an asset path or gate withdrawals. A change of underlying is only expressible as a NEW wrapper the user chooses to enter.
- **(v3.0.0) Permitted wrapper shapes.** A branded wrapper MAY be either **(a)** a `SparkPointMorphoVault` (full-bytecode CREATE2), or **(b)** a **Morpho Vault V2 Fee Wrapper**, provided that at deployment: `addAdapter` and `removeAdapter` are **abdicated** (exactly one child, permanently); `setReceiveSharesGate`, `setSendSharesGate` and `setReceiveAssetsGate` are **abdicated** (`abdicateNonCriticalGates: true`) so no gate can ever block a user; the **dead deposit** is the first transaction on the empty vault; the owner is the multisig (**never an EOA**); curator selectors carry a **≥3-day timelock**; the management fee is **0** and the performance fee **≤20%**; the name/symbol contain no "morpho" (Morpho naming restriction); and the child passes the on-chain eligibility check — `isVaultV2`, the three gate setters `abdicated`, `asset()` match, and a liquidity-ratio floor. **New `SparkPointMorphoVault` deployments are SUPERSEDED**; existing instances remain redeemable forever (N2). **(c)** a `SparkPointUniversalVault` deployed by `SparkPointVaultFactoryV2` as a `BeaconProxy` behind a TimelockController-owned beacon, with the child bound at initialization (no setter), the same 0-management / ≤20% HWM performance-fee invariants, and a role-gated scoped deployer that holds no upgrade, allowlist, pause, or fund power. **(v4.0.0)**

The **factory is deploy-only**: it holds no user funds, exposes no deposit/withdraw/sweep/rescue/migrate function, and retains NO privileged post-deployment authority (owner, pauser, guardian, or upgrader) over any wrapper it deploys — each deployed wrapper is self-governing under the same pause-only multisig/timelock. On `SparkPointVaultFactoryV2`, deployment is **role-gated to the scoped deployer** (a deterministic runner key; never the LLM agent) and limited to children already on the curated allowlist with fee/caps within hard on-chain bounds; the deployer has no other power. **(v4.0.0)** Because a wrapper's underlying Morpho vault charges its own fee, the **stacked fee MUST be disclosed net** to the user.

### VI. Spec-Driven Development (NON-NEGOTIABLE)

Work flows strictly: constitution → spec → plan → tasks → implementation. No implementation may begin without an approved spec and plan. Specs MUST define WHAT and WHY without leaking implementation detail; plans MUST pass the Constitution Check gate before tasks are generated; tasks MUST trace back to the spec. Cross-artifact consistency MUST be maintained — spec, plan, and tasks MUST NOT contradict each other or this constitution. Any change to scope, architecture, or invariants MUST be reflected back into the governing artifacts before code lands.

### VII. Simplicity & YAGNI

Depth over breadth; ship the narrow thing well. The system is MULTI-NETWORK: Base is live at launch and Sui is the designated fast-follow network, connected by a fully self-custodial bridge; networks BEYOND Base + Sui + **Robinhood Chain (mainnet 4663, ratified v3.0.0)** remain out of scope. The launch Aave vault remains single-purpose and single-vault, and each curated Morpho-wrapper vault is likewise single-purpose (exactly one curated vault each, bound for its entire lifetime) — these wrappers are RATIFIED scope under Principle V, not the deferred "multi-strategy vault" pattern. The following remain explicitly deferred and MUST NOT be built: multi-strategy vaults (market-neutral, volatility harvesting, yield optimization within a single vault); cross-vault yield optimization, auto-rebalancing or automated fund-routing between wrappers, and any meta-vault or router that moves user funds between curated Morpho vaults (the factory is deploy-only and each wrapper is bound to exactly one allowlisted child vault for its entire lifetime (admission remains Morpho-allowlist-scoped until separately amended)) — **(v3.0.0)** a single-child, adapter-abdicated **Fee Wrapper** is NOT a meta-vault: its adapter list is irreversibly fixed to one child at deployment, so it cannot move funds between vaults. **Discretionary curation by SparkPoint — market selection, cap-setting, or allocation — remains FORBIDDEN**; ZK trade proofs; SRK v2 utility and governance; KYC/compliance gating; protocols beyond Aave v3 / Aerodrome / curated-allowlist Morpho; stocks/TradFi; and a general-purpose financial assistant. Speculative generality MUST be rejected; build for the current milestone, not an imagined future. The Sui-side account/vault architecture and the bridge mechanism/provider are a SEPARATE follow-on technical design increment and MUST NOT be fabricated here; Sui is non-EVM (Move-based) and does NOT reuse the ERC-4337/4626 Base contract stack. Where the custom ERC-4337 stack threatens the schedule, the project MUST fall back to a battle-tested AA SDK (ZeroDev/Kernel) at the mid-build checkpoint, and any fallback MUST preserve the five non-custody invariants.

Two governance settings are scoped to this channel and change NOTHING about the vault or the five non-custody invariants:

- **Ownership — a single team-operated EOA is permitted for NON-CUSTODIAL operational contracts.** For the beta's SparkPoint-authored 4663 contracts that have NO fund-drain path by construction — the Sparky Broker NFT and its sale/activation contracts, the SRK utility token, the SrkFaucet, and comparable infra (with v3.2.0 the SRK token, the SrkFaucet and the custom testnet mint are **retired for the beta** in favor of the Pons token + OpenSea NFT — the same single-EOA + immutability policy applies to the beta's actual contracts) — a single team-operated EOA MAY hold the owner/guardian role in place of a multisig (developer-bandwidth-driven, operator aldrickb). This is safe ONLY because those contracts are, and remain, non-custodial and immutable (next bullet): an EOA owner may pause or tune bounded, hard-capped parameters but has no code path to move a user's funds — **N1 holds regardless of who the owner is.** The multisig requirement is UNCHANGED for any contract with a fund-custody or pause-of-funds surface: the Aave Yield Vault and every Morpho Fee Wrapper keep their multisig-governed, pause-only kill-switch (IV.3, N5) and the Fee Wrapper's "owner is the multisig, never an EOA" condition (Principle V). Shipping a value-custody vault under an EOA would be a SEPARATE super-majority re-ratification and is NOT taken here.
- **Upgradeability — value/provenance contracts stay IMMUTABLE; iterate by redeploy.** No value-bearing or provenance contract may become an upgradeable proxy under a single EOA. The two vaults (N5), the **SRK token** (fixed-supply, no-mint, no-owner), the **Sparky Broker NFT** (immutable provenance hash + fixed `MAX_SUPPLY`), the **BrokerRevenueDistributor** (no withdraw/sweep/rescue/migrate by construction), and the **BrokerActivationRegistry** (spends user SRK allowances, bounded by an immutable `maxPrice` ceiling) MUST remain immutable — a single-key upgrade over any of them converts a "no admin fund path" guarantee into a rug. Continuous development on these is achieved the constitution's OWN ratified way: deploy a NEW instance and rewire the entitlement (`SparkyBroker.setMinter/setActivator/setBaseURI-until-freeze`; a fresh sale/registry), never an in-place upgrade. Proxy upgradeability (UUPS or Transparent/ProxyAdmin) is permitted ONLY for (a) the already-upgradeable USER-owned ERC-4337 account, whose upgrade key is the user's own EOA and NEVER SparkPoint's (N3), and (b) optionally, fundless infra that custodies nothing (e.g. the deploy-only `SparkPointVaultFactory`, which the v4.0.0 contracts run behind a Transparent proxy so the implementation itself carries no upgrade and no payable surface); and **(c) (v4.0.0)** the wrapper **beacon** for custody wrappers, owned by a TimelockController under the IV.5/v4.0.0 authority rule (3-of-5 proposer, independent canceller, ≥72h delay) — the automated deployer holds NO upgrade power, and the beacon may be renounced once stable.
- **Honest disclosure (Principle III).** The beta's on-chain ownership and immutability posture MUST be surfaced truthfully wherever the app describes control. For the 4663 contracts the Trust Center / permissions copy MUST state that a single team-operated EOA holds the owner/guardian role (no multisig, no timelock) and that the contracts are immutable so that owner cannot change the rules or move funds — and MUST NOT assert a "2-of-3 multisig" for any 4663 contract that has none. A change to custody/upgradeability posture MUST land in BOTH changelogs (developer `CHANGELOG.md` + the client-facing in-app `/changelog`).

**Beta revenue model — Pons token + OpenSea NFT + companion revenue engine (ratified v3.2.0).** The beta adopts the Robin Brokers unified model: one utility TOKEN launched on the **Pons launchpad** (a bonding curve that graduates into a Uniswap pool — SparkPoint does NOT deploy the ERC-20; Pons mints it and its trade-fee stream is the creator revenue), a broker **NFT launched on OpenSea** (a SeaDrop **factory clone** — the only path that earns an OpenSea hosted-drop record on 4663; a self-deployed contract is display-only and shows a phantom "sold out"), and an **NFT-external revenue ENGINE** that accrues every fee source to a per-weight pot and pays **activated / fused** brokers. **SparkPoint deploys NO token or NFT contract of its own** — the token is a Pons contract and the NFT an OpenSea contract (we integrate their contract access, we don't own them); the only contracts SparkPoint deploys are the revenue subsystem (`RevenueSplitter`, the engine, `BrokerVault`, `RoyaltySink`) and the swap router. There is exactly **one** utility token. For the beta this SUPERSEDES the directly-deployed `SparkPointTestToken`, the custom `SparkyBroker` + `BrokerSale` mint, and the single-source pull `BrokerRevenueDistributor`. Proposal + full detail: `.specify/memory/constitution-amendment-v3.2.0.md`.

- **Fee sources → one pot, 90/10 holders/treasury.** Token-trade fees (Pons creator tax, routed through an immutable `RevenueSplitter` set as the token's `creatorFeeRecipient`), NFT royalties (OpenSea creator-earnings → a `RoyaltySink`), the own-router 0.20% swap fee, and — as they come online — vault performance fees and Premium payments, each via a permissionless feeder hop into the engine. Everything funds the fused NFTs.
- **Value rides a resale.** Earned value is delivered into a `BrokerVault` keyed by TOKEN ID (not wallet), withdrawable by per-token EIP-712 signature, so a broker carries its unclaimed rewards to its next owner.
- **Multi-asset, distributed AS-IS — SparkPoint's key divergence from Robin.** Robin's engine accepts ONLY ETH and its keeper **swaps** it into a payout asset before delivery. SparkPoint's engine accepts **ETH AND any ERC-20** and distributes each **as-is, with no conversion** — a **per-asset** weight accumulator, a `BrokerVault` that holds multiple assets per token id, and a `deliver()` that is a straight transfer (this also eliminates Robin's deliver-time swap gas-starvation failure). Distribution is **PUSH**: a keeper `settle()`s the accumulator and `deliver()`s each broker's per-asset share into its vault each round; holders withdraw when they wish — no per-period Merkle publish, no claim step.
- **Non-custody preserved (why this is a STANDARD amendment).** The engine, splitter, and vault hold PROTOCOL REVENUE (fees, royalties), never user deposits — **N1 holds**. They are value-bearing, so per the v3.1.0 policy they MUST be **IMMUTABLE / upgrade-renounced**: the 90/10 split and the no-drain / no-sweep guarantees must be bytecode, not a promise a single-EOA upgrade key could break. N1–N5, the non-upgradeable vault, the pause-only kill-switch, and the AI-disposition rule are UNCHANGED.
- **Solvency + timing invariants.** Any broker drop/half-drop MUST zero `weightOf` (not merely subtract from `totalWeight`) or a later permissionless settle over-pays into insolvency; every round boundary keys on `block.timestamp`, NEVER Robinhood's `block.number` (which differs from RPC height by ~89M).
- **Residual EXTERNAL trust — disclosed (Principle III).** Pons' owner can redirect the token's `creatorFeeRecipient` via a 3-day-timelocked setter (monitor `CreatorFeeRecipientChangeProposed`); post-graduation the Pons hook charges the fee in the swap's OUTPUT token and sweeping the token leg depends on Pons' keeper — so fee liveness partly depends on Pons. The Trust Center MUST state these honestly, alongside the single-EOA + immutable posture.

**Terminology.** "Fully self-custodial" is the canonical user-facing trust term (used in user-facing copy and the persistent trust badge). "Non-custodial / self-custodial" remain accurate technical descriptors in architecture text.

## Development Workflow & Quality Gates

- **Spec Kit flow.** Every feature MUST progress through spec → plan → tasks before implementation. The `plan.md` Constitution Check gate MUST pass; any violation MUST be resolved or recorded as an explicitly justified exception before tasks are generated.
- **Code review.** All changes MUST be reviewed against this constitution. Reviews MUST explicitly confirm the non-custody invariants (Principle I) and the AI-disposition rule (Principle II) are not weakened.
- **Contract testing.** Smart contracts MUST have unit and fuzz tests (Foundry) and MUST NOT reach mainnet without them.
- **Contract audit before mainnet custody.** No fund-custody contract (the Aave Yield Vault or any Morpho Fee Wrapper) may be deployed to ANY mainnet — Base mainnet OR Robinhood Chain 4663 — until the internal team's security audit and hardening are complete for that contract. **(v3.1.0)** The 4663 beta's NON-CUSTODIAL operational contracts (broker NFT / sale / activation registry / revenue distributor / SRK / faucet — no fund-drain path by construction, immutable) MAY launch on 4663 after a lighter internal security review rather than the full custody audit, PROVIDED they are beta-gated and their immutability + single-EOA ownership are disclosed per Principle III. The value-custody vault audit gate is UNCHANGED.
- **Simulation before sign.** No execution flow may ship that lets a user sign a transaction without first presenting a pre-trade simulation (from the fork simulator; vendor-neutral).
- **Beta-gating before real funds.** Real-fund exposure MUST begin only behind beta gating: whitelist, strict per-user and total caps, kill-switch armed, and geo-fenced frontend — via a small closed beta first, which **(v3.1.0)** runs on Robinhood Chain mainnet (4663) rather than a testnet, with nominal/test-scale funds and the caps + kill-switch armed.
- **Fallback checkpoint.** At the mid-build checkpoint, the custom AA stack is re-evaluated; if it threatens the schedule, the team falls back to a battle-tested AA SDK, and the fallback MUST be re-verified against all five non-custody invariants before proceeding.

## Governance

This constitution supersedes all other practices and conventions. When any spec, plan, task, or implementation conflicts with it, the constitution wins and the conflicting artifact MUST be corrected.

**Amendments.** Amendments MUST be proposed in writing with rationale and the affected artifacts, reviewed, and approved before they take effect. Dependent templates and artifacts (spec, plan, tasks, checklists) MUST be updated for consistency as part of any amendment.

**Re-ratification for custody changes.** Any amendment that touches the five non-custody invariants (N1–N5), the pause-only nature of the kill-switch, the AI-disposition rule, or the non-upgradeable vault semantics requires a super-majority approval and explicit re-ratification. Such changes MUST NOT be made implicitly through implementation.

**Versioning.** This constitution uses semantic versioning: MAJOR for backward-incompatible governance or principle removals/redefinitions, MINOR for new principles or materially expanded guidance, PATCH for clarifications and wording. The version line MUST be updated on every amendment.

**Compliance.** All PRs and reviews MUST verify compliance with these principles. Added complexity MUST be justified against Principles IV and VII; unjustified complexity MUST be removed.
