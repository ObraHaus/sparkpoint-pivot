Vault program, part 2 — AI-autonomous wrapping with an admin fast lane

Part 1 records what was built and deployed: the v4.0.0 fleet, the curator + P12 crawler, the runner apps, P11 wiring. Part 2 is the pivot. Because no wrapper was ever deployed, the admission model is being replaced before any vault exists: the AI curates, whitelists, and deploys wrappers on its own after a configurable cooling-off window; the operator keeps an instant whitelist/deploy lane; the timelock is confined to code and proxy upgrades. Amendment v4.1.0 (draft at .specify/memory/constitution-amendment-v4.1.0.md) carries the governance change.

Read this first. Nothing in this plan has been built yet — it is gated on the operator's review (V.1). The v4.0.0 contracts on 4663 hold no user funds and no wrapper was ever deployed, so the V2 factory can be sunset without migration. What stays live regardless: the curator, the admin panel, the web app, the keepers — and the custody invariants (no admin withdrawal, exits never gated).

1 · Why the pivot

Operator directive (2026-09-19). “I want the AI on its own to curate the list of Morpho vaults and deploy wrappers for them — with the additional control that an admin human can manually add or modify new vaults. The 3-day wait (6 days total) is not doable even if the constitution requires it; the client is already waiting. Reinforce the timelock only for code/proxy upgrades. AI can auto whitelist + deploy, but waits 1 day — configurable by an admin. Admin whitelist → immediate; admin can override and deploy immediately. One wrapper per whitelisted vault. Admin-whitelisted vaults are not the AI's to deploy.”
Part 1 path (superseded): Safe-A schedules setDeployer → 72h → execute Sep 22 · then a separate 72h timelock per vault to allowlist it · then a human queues each deploy. Every new vault waits days; the first deliverable slips to Sep 22–25.
Part 2 path: deploy the V3 factory → the AI admits and deploys on a 24h on-chain cooldown (no timelock involved) → the admin admits and deploys instantly from the panel. First vault live as early as Sep 20; every vault after that needs no waiting beyond the cooldown.

4 · The admission lifecycle

AI lane

  1. Curator publishes a new pick
  2. Runner calls whitelistVault(child) → readyAt = now + 24h
  3. Entry appears in the admin queue with a countdown
  4. After the cooldown the runner calls createVault
  5. Reports back → curated row flips to wrapped → deposit rail live

Admin lane

  1. Admin whitelists from the panel (wallet tx, instant)
  2. Deploys immediately (panel)
  3. Or cancels with unwhitelist

Override

Admin releaseNow(child) zeroes an AI entry's cooldown → deploy immediately.

Guardrails

  • One wrapper per child — on-chain revert on a second attempt
  • AI skips admin entries — runner checks whitelistedBy before acting
  • Cooldown bounds — 1h min · 7d max, admin-settable, evented
  • deployLimit — the timelocked per-day rate cap stays
  • Exits — never gated by admission or upgrade

7 · Governance & disclosure

Amendment v4.1.0 (MAJOR)

IV.5(b) changes from “no single key may add an entry / multisig + timelock” to “AI admission under an on-chain cooling-off window; admin instant admission; the timelock governs upgrades and non-admission parameters only.” That is a deliberate relaxation of an admission rule, so it is classified MAJOR and requires the operator's super-majority re-ratification. Draft at .specify/memory/constitution-amendment-v4.1.0.md.

  • The operator admin can admit and deploy a vault immediately.
  • Wrapper and factory code upgrade only through the 72h timelock; exits are never gated.
  • One wrapper per curated vault; fees performance-only above the high-water mark.
